## Executive assessment

**Overall: degraded, with production-capacity and reliability risks.** The repository has ten registered channel profiles and the parity checker passes, but capability in code is not the same thing as an actual successful release. The checked-in network snapshot records 147 video receipts (66 long-form, 81 Shorts), with 145 recorded as public. These are repository counts, not a fresh YouTube inventory.

1. **Production is serial across all ten channels.** One run was still on channel 6 after more than five hours, with four channel jobs waiting. That architecture makes late launches, missed slots, and long waits structurally likely.
2. **Covenant Shield is stale; Praise Garden and Guided Path have no published receipt in the snapshot.** Their jobs were waiting in the active production run, not proven failed. Neither a queued job nor an earlier credential preflight proves a launch.
3. **48 receipts have pending thumbnails:** 38 report permission refusals, six rate limits, and four other reasons. These are receipt-state counts, not live thumbnail checks. Some pending entries are Shorts, whose thumbnail behavior can differ from long-form.
4. **The locked Charon voice is not fully enforced.** A non-quota Gemini failure can fall back to Edge's `en-US-DavisNeural`; this conflicts with the project's stated permanent voice standard.
5. **Monitoring detects problems but can mislead.** A workflow marked successful may have skipped or failed a fail-soft component; the watchdog's stuck-run logic is based on whole-run age/status, not the current matrix job. Feedback files report zero measured long-form videos across the eight channels with artifacts.

## P0 — production throughput, missed slots and cancellation

### What actually happened

The live [scheduled production run](https://github.com/johnAzani/YouTube-automation/actions/runs/43310591718) was created at 10:28pm Thursday. Its plan completed at 10:59pm. GitHub's jobs API showed five completed legs, The Healing Balm rendering, and four remaining jobs queued at roughly 4:28am Friday. A [newer scheduled production run](https://github.com/johnAzani/YouTube-automation/actions/runs/43335854790) was pending. Status is a snapshot, not a forecast of eventual outcomes.

The five completed jobs took approximately **54, 49, 10, 49 and 84 minutes**, or 246 minutes total, excluding the plan and current sixth leg. The 10-minute job may have done less work; no assumption is made that every leg rendered a full video. An illustrative ten legs at this observed five-leg average would take about 8 hours 12 minutes per run. That is not a prediction, but it exposes the capacity risk against configured daily production start slots of **7:14am, 3:14pm and 8:14pm**—whose gaps are 8h, 5h, and 11h. The workflow also has a 24-hour long-form quota/cooldown policy, so three triggers do **not** mean three long-form uploads per channel per day.

The workflow sets `max-parallel: 1` because channel legs write shared `content/` state, and uses a workflow-wide `content-state` concurrency group shared with the authoring brain. This reduces simultaneous writes but makes rendering and uploading hold up other work. The [prior scheduled run](https://github.com/johnAzani/YouTube-automation/actions/runs/43245783974) ended cancelled while Covenant Shield was encoding; [issue #392](https://github.com/johnAzani/YouTube-automation/issues/392) records 25% progress and a ~32-minute remaining estimate shortly before it stopped. The visible evidence does not establish who or what caused that cancellation, and it does not prove an encoder defect.

### Why the supervisor is not sufficient

`scripts/scheduler_supervisor.py:stuck_runs` considers only workflow runs whose status is `in_progress` and uses **the workflow run's start time** against a fixed 210-minute threshold. A multi-channel matrix can legitimately last longer than 210 minutes while its individual jobs are working. Conversely, the GitHub API reported the currently active matrix run as `queued` even though one job was `in_progress`, so the status filter can miss work that is actually running. The 210-minute threshold also does not match the production job's configured 240-minute cap. This is a design risk; it is not proof the supervisor cancelled issue #392.

GitHub documents that, by default, a concurrency group permits one running and one pending run; a newer pending run replaces an older pending run even when `cancel-in-progress` is false. [GitHub concurrency documentation](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency) and [workflow syntax](https://docs.github.com/actions/reference/workflow-syntax-for-github-actions) explain the optional `queue: max` setting. Simply enabling a deeper queue could instead publish stale slots later or exhaust free quotas; it is not a complete solution. GitHub also explicitly says scheduled events may be delayed or dropped under load ([schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

**Recommended engineering order:** instrument per-channel job and stage start/end/progress; replace whole-run-age cancellation with an explicitly tested job-aware policy; redesign state writes/receipt persistence before introducing bounded channel-level parallelism; enforce idempotency and per-channel locks; distinguish stale catch-up slots from useful ones. Test with simulated long runs and concurrent commits before enabling on production. Do not cancel, re-dispatch or re-upload the active run merely to clear the queue: first reconcile live videos and receipts.

## P1 — voice standard, duplicate protection and receipt integrity

- `pipeline/prayer_pipeline.py:_narrate` uses Gemini Charon first and pauses on quota exhaustion, but falls back on other errors to `synthesize_edge(..., 'Charon')`. `pipeline/tts.py:synthesize_edge` maps a non-`en-` voice name to **`en-US-DavisNeural`**. Alignment failure has a fallback path too. This contradicts the Charon-only invariant documented in `STATE.md`; the function's production docstring also says no alternate voice. **Recommended:** make non-Charon speech fail closed for production, record the actual engine/voice in receipts, and test error and alignment-failure paths. Do not change the selected voice.
- The duplicate shield checks the authenticated channel's most recent **50 uploads** by exact or normalized title. Both the pre-check and `check_existing_channel_duplicate` can fail open on API errors. Renamed titles, videos older than the first page, or a failed lookup can evade this protection; a title match is not durable upload identity. Receipt recovery reduces risk but is not an absolute duplicate guarantee. Any changes must preserve safe recovery after an upload succeeds but the Git commit fails.
- The earlier branch work fixes expired quota-paused long-form jobs bypassing the regular duplicate-receipt and length checks, and fixes `--all` stopping after the first job. Those changes are **on this working branch only**, not deployed to `main`; they do not prove the live scheduler has been repaired.

## Prioritized action plan

1. **Now, observe rather than interfere:** track the existing matrix to completion; reconcile published videos and Git receipts for each leg, particularly Covenant Shield and the two launch channels. Escalate a specific failed leg with its run/job ID and stage. Never trigger replacements blindly.
2. **Before another scaling change:** redesign and test the stuck-run detector against queued/in-progress matrix jobs, real per-job timeouts, and 10-channel runs; avoid cancelling active renders just because total workflow age exceeds a single-job cap.
3. **Address throughput safely:** benchmark real stage durations and free quota per channel; isolate per-channel work and atomic receipt writes; use bounded parallelism only after duplicate prevention and state-commit race tests pass. Measure successful on-time uploads, not merely started workflows.
4. **Enforce Charon-only production** and expose a hard failure if the approved voice cannot be generated. Test normal, quota, model-error and alignment-error cases.
5. **Triage thumbnails by error type** using read-only current status first; repair permissions or scopes only after evidence, honor rate-limit backoff, and separately fix poster safe-zone errors.
6. **Fix telemetry:** show per-channel last actual upload, live/recorded distinction, matrix position, current stage and receipt status; stop implying all channels are blocked; investigate zero measured feedback data; publish no fabricated watch-hour or CTR figure.
7. **Fix quoted time values and validation**, and label Short target times as editorial targets unless a real scheduler enforces them.
8. **Review originality, rights and YPP status per channel** before scaling publishing volume. More videos alone do not demonstrate viewer satisfaction or policy eligibility.
